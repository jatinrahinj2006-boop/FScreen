# FScreen

**Pane-relative fullscreen** for Chrome/Edge (Manifest V3).

FScreen expands the player to fill **only the browser tab viewport** instead of
the monitor. Split-screen keeps working: your second pane is untouched, the OS
taskbar stays visible, and a second monitor stays usable.

```
┌───────────────────────────────┐  ┌──────────────────────────┐
│ browser tab                   │  │ your other pane          │
│ ┌───────────────────────────┐ │  │                          │
│ │ video (fills the tab)     │ │  │  still right here        │
│ └───────────────────────────┘ │  │                          │
└───────────────────────────────┘  └──────────────────────────┘
       pane fullscreen                    real fullscreen would
                                         have eaten both
```

There are **two triggers, kept separate on purpose**:

| Trigger | Result |
| --- | --- |
| `` Alt+` `` | **Our pane-relative fullscreen** — always available, in whichever tab has focus. |
| `F`, or the site's own fullscreen button | **Real fullscreen.** FScreen does not touch it, so the site behaves exactly as if we were absent. |
| Toolbar icon (badge `ON`) | *Opt in* for this tab: from now on the site's `F`/button fullscreen is redirected into the pane instead. |

## Install (load unpacked)

1. Open `edge://extensions` or `chrome://extensions`.
2. Turn on **Developer mode**.
3. Click **Load unpacked** and pick this folder (`D:\FScreen`).
4. Grant site access when asked — the extension ships `host_permissions` for the
   sites it supports, so normally nothing extra is needed. If a site does not
   respond, click **Details → Site access → Allow on all sites** for that
   extension.

Confirm it is alive: any allowlisted page should have `data-fscreen="1"` on
`<html>`.

### Files

```
manifest.json              allowlist, permissions, content-script registration
```

## Controls

| Action | Result |
| --- | --- |
| `` Alt+` `` | Toggle pane-relative fullscreen on/off for this tab. Works whether interception is on or off. |
| `F` / the site's fullscreen button | **Real fullscreen** — FScreen stays out of it (unless interception is ON for the tab, see below) |
| `Esc` | Leave pane-relative fullscreen (and unwind any nested frame) |
| Faded round button, top-right corner | Mouse-only exit; opacity `.16` at rest, full on hover |
| Toolbar icon click | Toggle interception **for this tab** (badge `ON` green / `OFF` red) |
| `chrome://extensions/shortcuts` | Bind a browser-wide key to the same toggle |

**Interception `OFF`** (badge red, **the default**) → nothing of ours touches the
site's own fullscreen: `F`, its button and `<video controls>` really go
fullscreen, no styles, no exit button. `` Alt+` `` is your key and still works.

**Interception `ON`** (badge green, per tab, opt-in) → every fullscreen the site
asks for is redirected into the tab pane instead. That is the mode for when you
*are* split-screening and want the site's own button to behave too. The site's
`F` key and button then toggle our pane on and off as normal.

### Why `` Alt+` `` is handled in-page

Chrome reserves `Alt+F` for its own menu, and `commands.suggested_key` does not
accept a backtick, so the shortcut is a capture-phase `keydown` listener in the
MAIN-world script. `commands.toggle` still exists so you can bind a key at
`chrome://extensions/shortcuts`.

Binding a key there also changes *who delivers it*: Chrome hands the command to
the service worker, which forwards it to the top frame of the active tab. That
works even when your focus sits inside a frame FScreen does not cover (an ad, or
an embed host that is not allowlisted yet) — one of the reasons `` Alt+` `` can
otherwise appear dead.

**Neither path ever stands down.** One physical key can reach us twice — as a
`keydown` in the focused frame *and* as a command in the top frame — and the
second copy used to toggle the pane straight back off, which reads as "the
shortcut did nothing". Both paths now act, and a short window (250 ms, 400 ms
when the key is the one bound at `chrome://extensions/shortcuts`) drops the
duplicate: a frame ignores a command it just handled, a parent ignores one when
an embed signalled first, an embed ignores a key its ancestor already took.

Two more ways a key used to die:

* **Focus in a frame with no player** — an ad, a logo link, a secondary embed.
  The `keydown` only reaches that frame, it resolves nothing, and no other
  frame ever hears about the press. It now hands the key to its parent, which
  keeps walking up until somebody owns a player.
* **The site replaces the player box while the pane is open** (SPA re-render,
  episode change). The pane was dropped silently, so the next press opened it
  and the render after that closed it again. It now re-arms on whatever
  replaced the player.

## Adding a site

Two edits, nothing else.

**1. `manifest.json`** — add the pattern to *both* `host_permissions` and *both*
`content_scripts.matches` arrays (there are two content-script entries, the
ISOLATED one and the MAIN one):

```jsonc
// host_permissions + each "matches"
"*://newsite.example/*",
"*://*.newsite.example/*"
```

**2. `src/content-main.js`** — optionally add an entry to `SITE_CONFIG`:

```js
'*.newsite.example': {
  playerSelector: '#player-wrapper',   // the element that should fill the tab
  fullscreenButtonSelector: null       // optional, informational for now
},
```

`playerSelector` accepts a comma list and crosses shadow roots. If you skip it,
the generic resolver still works: nearest ancestor that owns a `<video>`, or for
cross-origin embeds the biggest **visible** iframe (hidden `about:blank` provider
frames are filtered out by `isLiveFrame()`).

Whichever path finds the player, the answer is then trimmed to the box that
*owns* it (`tightenToPlayer()`): a wrapper that also owns page content of its
own — a server list under the player, season rows, an episode grid, a related
rail — is a page section, not the player, and expanding that would leave the
rest of the page sitting inside the black rectangle. Small rows directly under
the box (a control bar) still count as part of the player and come along.

Because `<html>` gets `data-fscreen="1"`, you can verify a new site immediately
in DevTools:

```js
document.documentElement.dataset.fscreen   // "1" = armed
```

### Two rules for `src/content-main.js`

Both of these were real bugs found against YouTube, and both fail *silently* —
the site's own code swallows the error and the user just sees "the fullscreen
key does nothing".

1. **Never use `innerHTML` / `insertAdjacentHTML`** in a content script. It runs
   in the MAIN world, so sites that ship
   `Content-Security-Policy: require-trusted-types-for 'script'` (youtube.com
   does) make the assignment throw. The exit button is built with
   `createElementNS` for that reason, and `enterPseudo()` no longer lets a
   failing UI step skip the `fullscreenchange`/`resize` events — without them
   the player never re-measures its video and keeps its old pixel sizes.
2. **`document.fullscreenElement` must report what the page asked for**, not
   the element we chose to restyle. Players compare the two before calling
   `exitFullscreen()` (YouTube only exits when `fullscreenElement` equals the
   element it requested), so answering with a different element makes their
   toggle one-way. The hotkey has no request behind it, so it answers with
   `document.documentElement` — the page-level request those players make
   themselves. Measured on youtube.com: answering with the player instead left
   `F` doing *nothing at all*, both while our pane was up and after taking over
   from real fullscreen.

### Finding a site's embed host

Video sites usually stream from a different domain than the page you are
watching on, and FScreen needs a match pattern for **both**.

1. Open the watch page → DevTools → Elements → search for `<iframe`.
   Note its `src` host. That is your primary embed host, e.g.
   `anikototv.to` → `megaplay.buzz`, `hianime.at` → `zokoanime.video`.
2. Check the other server tabs. On Next.js players the inactive ones are often
   `<iframe src="about:blank">` stubs that get navigated later — click each
   server tab and read the new `src`.
3. If there is no iframe at all, the video may be in the page itself: search for
   `<video`.
4. Sites that hide the host behind an API need the request chain traced in the
   Network tab. For anikototv.to that chain was:

   ```
   GET ajax/episode/list/<id>?vrf=<anything>     header: X-Requested-With: XMLHttpRequest
     -> data-ids
   GET ajax/server/list?servers=<ids>            -> data-link-id
   GET ajax/server?get=<link-id>                 -> result.url  (the megaplay host)
   ```

   Direct fetches of such embed URLs often need `Referer: https://<parent-site>/`
   or they answer `410`.

`match_about_blank: true` is already set, so FScreen is also armed inside
`about:blank` stub frames (their origin is the parent's, which is allowlisted).
Once such a frame navigates to a third-party host, that host needs its own
pattern.

## Permissions, and why

| Permission | Reason |
| --- | --- |
| `activeTab` | Toolbar-icon toggle for the tab you are looking at. |
| `storage` | The per-tab ON/OFF flag (`chrome.storage.session`). |
| `host_permissions` per site | Lets the MAIN-world script run on those origins. It is the entire allowlist — one entry per supported site, nothing broad (`<all_urls>` is not used). |

No remote code, no analytics, no network calls of our own. The background worker
only reads/writes the per-tab flag and sets the badge. Everything else runs in
the page's own world, which is the whole point.

## How it works

1. **`world: "MAIN"`, `run_at: document_start"`** — the override has to patch the
   *page's* `Element.prototype`. An ISOLATED-world patch touches a different copy
   of the prototype that page scripts never see. Verified by the test suite: the
   first inline `<script>` in `<head>` already sees `function fakeRequest`.
2. **`fakeRequest()`** checks the tab's mode first: with interception off it
   hands the request straight to the browser (that is the "F means real
   fullscreen" behaviour). Otherwise it walks up from the requested element to
   the real player container (bounded growth: it follows a parent only while
   that parent is basically the same box, so a wrapper is picked but a
   page-level section is not), then applies `position: fixed; top/left: 0;
   width: 100vw; height: 100vh; z-index: 2147483647; background: #000`.
3. **Containing blocks are neutralised** — any ancestor with `transform`,
   `perspective`, `filter`, `backdrop-filter`, `will-change`, `contain` or
   `transform-style` would make `position: fixed` resolve against that ancestor
   instead of the tab. Saved on enter, restored on exit. Page scroll is locked.
4. **The page is told the truth-ish** — `document.fullscreenElement` returns the
   element *the page asked for* (`` Alt+` `` had no request behind it, so it
   answers `<html>`, see rule 2 above), and synthetic `fullscreenchange` +
   `resize` events are dispatched, so player UIs and postMessage bridges think
   fullscreen is active instead of spinning on "enter" forever.
5. **Cross-frame cooperation** — when an allowlisted embed expands itself it
   posts `child-expand` upward; the parent stretches the `<iframe>` element to
   fill the tab. `Esc` in the top document unwinds the child first, then itself.
6. **Native-fullscreen rescue** — anything that still reaches *real* native
   fullscreen while the mode is ON (the browser's own `<video controls>` button,
   an embed host that is not allowlisted yet, a player that cached the original
   API) is converted back to pane-relative fullscreen on the `fullscreenchange`
   event. With the mode OFF this handler does nothing.
7. **MutationObserver housekeeping** — SPA re-renders (and site resize handlers
   writing `el.style.height`) that drop or rewrite our inline sizing are
   re-asserted; a removed player exits cleanly; a page that re-patches
   `requestFullscreen` behind our back is re-patched every 250 ms. Driven by
   `setTimeout`, not `requestAnimationFrame`, because rAF does not run in a
   background tab. The style re-assert compares `position`/`width`/`height`
   only — enough to catch every real clobber — so it cannot turn into a
   write loop against a page that rewrites our style every frame.

## Troubleshooting

**Start with the ✕ button — no DevTools needed.** Open the pane (`` Alt+` ``)
and hover the faded round button in the top-right corner. It reads:

```
FScreen 1.4.0: pane on div#player-aspect 937x854 - click or Esc to exit
```

* **The number is the build that is actually running.** If it is not `1.4.0`,
  the files were edited but the extension was never reloaded — press ⟳ in
  `chrome://extensions` (the card itself must read Version 1.4.0) and then
  refresh the tab, because content scripts only inject into documents that load
  afterwards. The toolbar icon's tooltip carries the same number.
* **The element after `pane on` is the whole diagnosis.** If it is a wrapper
  that also owns page content instead of the box holding the player, that
  element is what I need to fix target resolution for the site.
* In the console, `document.documentElement.dataset.fscreenBuild` gives the same
  build, and pressing `` Alt+` `` logs it:

```
[FScreen] ready 1.4.0            <- current build is running in this document
[FScreen] pane on -> div#player-aspect (937x854)
[FScreen] pane off -> div#player-aspect
[FScreen] no player in this frame - passed the key to the parent frame.
[FScreen] command ignored: that keypress was already handled.
```

**`` Alt+` `` does nothing**

1. **Is the site covered?** FScreen only runs on the origins in the allowlist
   (the Sites table above). In DevTools check
   `document.documentElement.dataset.fscreen` — `"1"` means armed, `undefined`
   means this page has no content script and nothing of ours will ever fire.
   Send me the site and I will add it.
2. **Where is the focus?** Key events go to the frame that has focus. A frame
   that owns no player (an ad, a logo link) now passes the key up to its
   parent, but a frame with **no FScreen at all** — an embed host that is not
   allowlisted yet — still swallows it. Click the page outside the embed, or —
   better — bind the shortcut at `chrome://extensions/shortcuts`, which makes
   Chrome deliver it to the extension itself no matter where focus is.
3. **Look at the console.** `[FScreen] Alt+` pressed, but no player found in
   this frame.` means the resolver came up empty even at the top of the page
   (no `<video>`, no visible iframe). Tell me the site; the generic resolver may
   need a `playerSelector` for it. `[FScreen] pane ignored: ...` /
   `[FScreen] command ignored: that keypress was already handled.` are the
   de-duplication window doing its job, not a failure.
4. **After reloading the extension**, refresh the tab. Content scripts are only
   injected into documents that load afterwards.

**The pane opens, but the video keeps its old slice and the rest of the page is
still on screen**

Confirm what happened with the `[FScreen] pane on -> …` line — if it names a
wrapper rather than the player box, that is the resolver picking a wrapper that *contains* the player but also owns
page content of its own (a server list, seasons, an episode grid) instead of the
player box: everything under it ends up inside the black rectangle. Reload the
extension (⟳) and refresh the tab — the answer is now trimmed to the box that
owns the player (`tightenToPlayer()`, case E of the suite). If it still happens
on a site, add a `playerSelector` pointed at the box that directly holds the
`<video>` or the `<iframe>`.

**The pane is up, but the site's header/menu bar is still across the top of it
(half works, "some site content is still there")**

That is not the resolver — the ✕ tooltip names the right box — it is the box
being trapped in a stacking context. `z-index: 2147483647` is only compared
against the siblings of the nearest context above the element, so a wrapper like
the anime watch pages' `div.anis-watch-wrap { position:relative; z-index:3 }`
pins the pane at level 3 while the site's fixed header sits in the root context
at 9999 and keeps painting on top. `neutralizeAncestors()` now releases every
stacking-context-creating property on the way up (`z-index` → `auto`, `opacity`
→ `1`, plus isolation/blend/clip/masks/individual transforms), so the pane joins
the root context where `2147483647` really is the maximum; `housekeep()` puts
those back if the site rewrites them, and `exitPseudo()` restores them.

Reload the extension (⟳), refresh the tab, open the pane and confirm two things:
the ✕ tooltip must read `FScreen 1.4.0`, and nothing but the pane may be hit at
the top of the page. `node tools/leftover-probe.mjs <watch-url>` runs that check
for you; if a site still shows something, send me the `pane on -> …` line and
whatever element wins `document.elementFromPoint(20, 20)`.

**An error box says `Failed to execute 'requestFullscreen' on 'Element': API
can only be initiated by a user gesture`**

That one is the **site**, not FScreen — and since 1.4.0 it no longer reaches
the page at all. anikototv.to does it literally, in `anikoto/js/main.js`:

```js
function checkIframeSrc(){ let t = setInterval(() => {
    let i = document.querySelector("#player iframe");
    i && i.src && (requestFullscreen(), clearInterval(t))   // <- from a TIMER
  }, 500) }
function requestFullscreen(){ let t = document.querySelector("#player iframe");
    t.requestFullscreen ? t.requestFullscreen() : … }       // <- Element.prototype
```

After an episode change it polls for the next iframe and then asks for
fullscreen from a `setInterval` callback. By then the click or keypress is
long gone, so the browser refuses. Nothing can grant it a gesture that the page
consumed itself.

Two things follow:

* **Our file is in the stack because we *are* `Element.prototype.requestFullscreen`
  — not because we broke it.** Measured on that exact URL, with the same call,
  with and without the extension:

  ```
  without FScreen  window handler saw: "Permissions check failed"   <- the overlay
  with FScreen 1.4.0  window handler saw: (nothing)
                      page still got:    rejected: Permissions check failed
                      console:           [FScreen] fullscreen request rejected: …
  ```
  Identical rejection either way; only the top of the stack differs (`main.js`
  without us, `src/content-main.js` with us).
* **1.4.0 defuses it** (`defuseGestureRejection()`): a handler is attached to
  the promise we hand back, so the rejection never reaches
  `window.onunhandledrejection` and the site's overlay has nothing to draw. The
  page still receives the *same rejected promise* — its own `.catch`, when it
  has one, still runs — and only the no-gesture case is defused; a genuine
  failure still surfaces as before. Case H of the suite covers this, with a
  control rejection proving the window handler really is working.

If you still see that box, you are running an older build: your stack showed
`fakeRequest` on **line 858**, while 1.4.0 makes that call on line 1048 (its
`function fakeRequest` starts at 1043). ⟳ reload the extension and refresh the
tab — the ✕ tooltip must read `FScreen 1.4.0: …`.

**The pane opens and then closes by itself, or the shortcut only works every
other time**

That is the site re-rendering the player while the pane is on it. `housekeep()`
now re-arms on whatever replaced the player instead of dropping the pane, so
this only survives if the site removes *and* leaves no player (an ad slot, an
episode that has not loaded). If a page still flickers like this, the console
shows `pane off -> …` followed immediately by `pane on -> …`; send me both
lines.

**`F` triggered FScreen** — that only happens when interception is ON for the
tab (badge green). Click the icon once to put it back to the default OFF.

## Known limitations

* **The rest of your site list has not been added yet** — YouTube, anikototv.to,
  megaplay.buzz, cinehd.vc and hianime.at are wired up; more sites need their
  match patterns (and ideally their embed hosts).
* A fullscreen request issued by an embed host that is *not* allowlisted only
  gets converted after the fact (the rescue in step 6 above), so you may see a
  one-frame flash. Adding the embed host to the manifest fixes it properly.
* If a site draws its own player chrome in a sibling overlay outside the element
